Event-driven architecture

Transactional Outbox and Redis Streams

Problem

Post creation used Spring Application Events and @TransactionalEventListener(AFTER_COMMIT) to separate statistics updates, notifications and search indexing from the core operation.

Database connection pressure

  • REQUIRES_NEW opened another transaction on the same thread, so a single request could occupy two database connections simultaneously.
  • Slow secondary processing also kept the main transaction’s connection occupied, increasing the risk of pool exhaustion and deadlocks under concurrent load.

Event loss after a commit

@Async with AFTER_COMMIT improved transaction separation, but an asynchronous task could fail during a server outage. Without durable storage or retries, the event could be lost.

Solution

Record the business change and its Outbox event in one database transaction, then deliver the event asynchronously.

Post + Outbox row→Database commit→Async publisher→Redis Streams→Consumer / handler
  1. At BEFORE_COMMIT, save the post and Outbox record in the same transaction.
  2. After the commit, use AFTER_COMMIT + @Async to read the Outbox record and publish it to Redis Streams.
  3. Consumers process stream messages and dispatch them to the appropriate handler.
  4. A scheduler republishes events when immediate publication fails. Recover pending messages with XCLAIM after consumer failures, and mark repeatedly failing events as FAILED using retryCount.
  5. Use a dispatcher and the strategy pattern to add event types without changing existing core service code.

Results

  • Durable Outbox records prevent events from being lost solely because an asynchronous task fails; failed events can be reprocessed.
  • Secondary work runs independently of request completion. Notification or statistics failures do not affect the main transaction.
  • Handler separation improves extensibility and maintenance.
  • Retry counts and custom metrics support failed-event tracking and operational monitoring.

Search architecture

LIKE → MySQL Full-Text Search → Elasticsearch

Problem

Search used QueryDSL containsIgnoreCase(), generating LIKE '%keyword%'. With no fixed prefix, the database could not use a B-tree range scan and performed a full table scan. Search, sorting and pagination became slower as the dataset grew, with response times reaching 60,735 ms.

First improvement: MySQL Full-Text Search

  • Used an inverted index to narrow candidate rows without introducing a separate service.
  • Added a FULLTEXT index with an n-gram parser; the documented configuration included innodb_ft_min_token_size=2.
  • Implemented a custom Hibernate dialect using FunctionContributor to expose MATCH … AGAINST to JPA, and sorted by relevance score.
  • Reduced p95 response time to approximately 82 ms.

Remaining limitations

The full-text result set could not be combined with B-tree sort fields such as created_at and rate through a composite index. Large result sets required filesort. For infinite scrolling, cursor filters such as post_id < ? were applied after scanning the full-text results, so deeper pages still degraded.

Final solution: Elasticsearch

  • Used the Nori Korean morphological analyzer to reduce excessive matching from n-grams.
  • Implemented cursor pagination with search_after, sorting by createdAt DESC, post_id DESC; the ID is a tie-breaker.
  • Indexed only search-related fields in PostDocument. Elasticsearch returns post IDs; MySQL retrieves entities with findByIdIn.
  • This hybrid structure preserves JPA relationships, avoids mapping full search documents back to entities and keeps the index small.
Search request→Elasticsearch: matching + sorted IDs→MySQL: entity retrieval
Methodp95 response time
LIKE60,735 ms
MySQL FTS82 ms
Elasticsearch78 ms

Results

Reduced response time from 60,735 ms to 78 ms, approximately 99.8%, while maintaining stable responses on a large dataset and separating the search model for future expansion.

Concurrent post statistics

Likes, comments and view counters

Problem

Requests concentrate on individual posts. A SELECT → increment → UPDATE sequence can lose updates under concurrency. Frequently updating indexed counters also adds B-tree maintenance, page splits and redo/undo logging overhead. A JVM synchronized lock cannot coordinate multiple application instances.

Solution

Moved counters into a dedicated PostStat table to isolate frequent updates from the larger Post row and reduce update overhead.

Comparison setup

Used k6’s constant-arrival-rate executor for 30-second runs at 10, 50, 100, 150, 200 and 300 RPS. Test hardware: AMD Ryzen 5 3600 and 16 GB RAM.

Compared correctness (actual database increments / requests), p95 latency, failure rate, CPU usage and operational complexity.

ApproachObserved behavior / trade-off
No lockCorrectness fell to 58.6% as load increased.
Pessimistic lockingMaintained 100% correctness, but resource contention increased latency with load.
Optimistic locking + retriesHot-row conflicts produced a failure rate of up to 98.5%.
JPQL atomic updateAchieved 100% correctness and 71 ms p95 without additional infrastructure.
Redis distributed lockLock acquisition timeouts and round-trip overhead caused failures to spike at 300 RPS.
Redis write-behindLowest p95 at 14 ms and lower database index-update load, with additional operational complexity and loss-recovery design requirements.

Decision and results

Selected JPQL atomic updates for the current traffic level: they provided stable latency and CPU use while retaining 100% correctness without additional infrastructure. At 300 RPS in the load test, p95 was approximately 71 ms.

Redis write-behind remains an option if database index-update costs become the bottleneck as traffic grows.

Daily post reindexing

Problem

Changes to user dictionaries and synonym dictionaries require reindexing. Asynchronous indexing can also leave Elasticsearch inconsistent with MySQL: existing posts may be missing from search, or deleted posts may remain in results. A database commit can succeed even when an event listener fails or an indexing request is lost during a network or Elasticsearch outage.

Solution

Treat the database as the source of truth. Build a new index, reindex the dataset and switch the search alias without downtime. If the batch fails, the existing index continues serving search.

Database snapshot→New index→Full reindex→Alias swap→Catch-up changes

Preserving changes during the batch

  • Record watermark T0 = (modified_at, id) when the batch begins.
  • Record T1 immediately after the alias swap, then replay database changes in (T0, T1] into the new index.
  • Use a Painless script to update a document only when DB.modified_at > ES.modified_at, preventing catch-up processing from overwriting a newer document already indexed by a real-time listener.

Handling replica lag

Check replication consistency using GTIDs before taking a snapshot from a replica. Read catch-up changes from the primary to avoid replication-lag gaps.

Results

  • Each reindexing run applies dictionary changes.
  • The same pipeline can support additional batch work, such as computing popular posts.
  • The daily batch reconciles search data against the database and repairs inconsistencies.

Distributed notifications and FTS queries

Preventing missed SSE notifications

Problem

After scaling out the application, real-time notifications were occasionally missed. Each user’s SSE session belonged to a specific server. An event produced on another server could not reach that session.

Solution

Event-producing server→Redis Pub/Sub→All application instances→Matching local SSE session
  • Publish a message containing the target user ID to a Redis channel.
  • All application instances subscribe to the channel.
  • Each instance checks its local session store and sends the SSE message only if it holds the target user’s session.

Result

Enabled notification routing across application instances, removing the server affinity constraint on scaling and improving the real-time user experience.

Restoring full-text index usage

Problem

A full-text query took 13.8 seconds to return 11 results:

MATCH(post.title) OR MATCH(experience.name)

EXPLAIN ANALYZE showed roughly one million post index lookups and one million nested-loop joins against experience, with the OR filter applied at the end.

Solution

  1. Query IDs using MATCH(post.title).
  2. Query IDs independently using MATCH(experience.name).
  3. Merge the IDs into a deduplicated set in the application.
  4. Fetch-join only the final 11 IDs.

Splitting the OR into independent, union-like queries lets each branch use its own full-text index and filters rows before joining.

Results

Reduced search response time from 13.8 seconds to 82 ms, with stable responses on approximately one million records.

JPA query optimization

JOINED inheritance: limiting rows before joining

Problem

Experience used @Inheritance(strategy = JOINED) and @DiscriminatorColumn, with Place and Video subtype tables. Fetch-joining the hierarchy added LEFT JOINs regardless of the discriminator value.

The optimizer replaced an index-ordered nested-loop plan that could stop after LIMIT 11 with a hash-join plan that read and joined approximately one million rows, sorted them and then retained 11. The query took 88 seconds.

Solution

Covering index: select 11 post IDs→Fetch-join only those IDs
  1. Select only post.id through a covering index, completing the sort and limit at the index level.
  2. Use WHERE post.id IN (ids) to retrieve details for those 11 rows. Subtype joins then operate on a bounded input, with approximately 11 loops.

Results

  • Reduced query response time from 88 seconds to 0.31 ms.
  • Compared with the earlier normal-state baseline of 0.42 ms, this was a further 26% reduction.

N+1 queries with a nullable one-to-one relationship

Problem

The comment API executed 16 queries despite a fetch join. Comment ↔ CommentStat used a nullable inverse-side @OneToOne(mappedBy) relationship. Hibernate issued extra SELECTs to determine whether the related row existed, so LAZY loading behaved like eager loading.

Solution

Switched the read-only API to DTO projection. Selecting only the required columns avoids entity loading, relationship traversal and Hibernate proxy checks.

Results

Queries per request161

Removed 15 queries and reduced response time by approximately 28%.

Reindexing batch performance

Problem

The Elasticsearch reindexing batch targeted approximately two million records. After more than three hours, progress remained below 30%. The recorded baseline stalled at approximately 600,000 records after more than 3 hours 20 minutes.

EXPLAIN ANALYZE showed seven tables LEFT JOINed around post. The plan joined and sorted approximately 1.29 million rows before applying LIMIT 2000. One query took about 900 seconds.

First improvement: deferred joins

  1. Select 2,000 post IDs using a covering index so sorting and limiting finish at the index level.
  2. Join detail tables only for those IDs, bounding the input at 2,000 rows. Branch by dtype to avoid unnecessary Place/Video joins.

Reduced query time from 900 seconds to 1.46 seconds and total batch time to 31 minutes.

Remaining bottleneck

A rough estimate of 1.46 seconds × 500 pages suggested more than 11 minutes, yet the batch took 31 minutes. Analysis identified accumulated random disk I/O from repeated single-row index lookups during the join stage.

Second improvement: Spring Batch partitioning

Partitioned the modified_at range. Each worker step independently performed the read → process → write sequence.

Partition step→Worker steps by modified_at range→Elasticsearch bulk indexing

Result

Completed the two-million-record reindexing batch in 8 minutes 15 seconds after query restructuring and partitioning.

Architecture and persistent login

Rebuilding the application architecture

Problem

Frontend and backend logic were coupled in Meteor.js, making the impact of maintenance changes difficult to assess. The User–Factory–Worksite–Checklist domain was relational, but the MongoDB design did not enforce referential integrity, allowing orphaned records.

Solution

  • Introduced an Express.js backend with a layered architecture and explicit responsibilities.
  • Used React and Redux-Saga to separate asynchronous workflows from state management on the frontend.
  • Migrated MongoDB data to MySQL, enforcing relationships through foreign keys and ON DELETE CASCADE, with indexes for query performance.

Results

Reduced code-analysis time during maintenance. ACID transactions and enforced relationships improved data consistency in production.

Keeping users signed in

Problem

The WebView app frequently signed users out despite its automatic-login setting.

  • The Express backend used MemoryStore, so restarting or deploying the server removed all sessions.
  • WebView cookies were not always written to disk before the Android app process terminated, causing login cookies to be lost.

Solution

Login succeeds→Persist session in MySQL→CookieManager.flush()→Restore login after restart
  • Moved Express sessions to MySQL with express-mysql-session, allowing session recovery after a server restart.
  • Called CookieManager.flush() after successful login to immediately persist in-memory cookies to device storage.

Result

Preserved automatic login across server restarts and forced app termination, improving the user experience.
