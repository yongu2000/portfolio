Session Recovery After a Lost Response

Problem

The session needed to survive a lost token-refresh response or app termination without logging out a legitimate user during a retry.

Distinguishing legitimate retries from token replay

  • Allowing a previously used token for recovery must not also allow an attacker to replay a stolen token.
  • Request identity had to survive app termination so the server could recognize a legitimate retry.

Solution

Persist request identity before refreshing

  • Store the token pair and pending request ID as a single secure-storage value before sending the refresh request.
  • After a restart, resend the same installation proof and request ID.

Commit token rotation and the recovery response atomically

  • Under a session-row lock, consume the old token, issue new tokens, and store the encrypted recovery response in the same transaction.
  • Encrypt the recovery response with AES-256-GCM using a separate key.

Return the same response only within a bounded recovery window

  • Require the same installation proof and request ID within the default 90-second recovery window.
  • Return the previously issued token pair only if the successor token is unused and the request matches the current token refresh history.
  • Revoke the session and reject authentication on mismatched conditions, an expired window, or reuse of a token from an earlier refresh step.

Results

Session recovery despite response loss and app termination

  • Even after two consecutive lost responses and forced app termination, restarting the app resumed the refresh and restored the same account and World.
  • Legitimate retries returned the previously issued token pair without another rotation or an extension of its validity.

Replay blocked outside the allowed recovery conditions

  • PostgreSQL-backed tests covered concurrent requests and recovery-window boundaries, confirming that token reuse outside the recovery conditions was rejected.
2

AI Job and Credit Consistency

Problem

The design needed to prevent duplicate credit consumption, even when requests were duplicated or jobs were retried after a Worker failure.

Handling retries and out-of-order completion

  • Attempts whose execution validity had expired had to be excluded from finalization.
  • Reserved credits had to be released on terminal failure.
  • Results that completed later had to be prevented from overwriting the result the user had already selected.

Solution

Approve the job and reserve its credit atomically

  • Persist the input snapshot, credit reservation, and QUEUED job in the same transaction.
  • Reuse the existing job when a request repeats the same operation key and body.

Validate ownership for each execution attempt

  • Claim a job with SKIP LOCKED, then assign an attempt ID and an execution-validity window.
  • Close the short transaction before calling the external AI service.
  • Immediately before finalization, recheck the current attempt ID, validity window, permissions, and reservation state.

Separate finalization, credit settlement, and user selection

  • Commit the successful candidate and credit consumption in the same transaction.
  • Retries retain the same reservation; a failed or invalidated job releases it.
  • Store completed outputs as candidates. Replace the Active result only when the user selects one.

Results

Stale results rejected and credit consistency preserved

  • PostgreSQL-backed regression tests confirmed that stale attempts could not finalize results and that the user's selection was preserved even when jobs completed out of order.
  • Tests confirmed that requests competing for the last credit did not consume it twice, and that terminal failure released the reserved credit.

Generated outputs remained consistent with user selection

  • In the Android app with a test Provider, selection, editing, undo, and deletion were reflected in the map and feed.
  • External AI calls may be retried, but internal result finalization and credit consumption were protected against duplication.

Improving Search Architecture

Problem

Search latency at scale

  • As the dataset grew, LIKE %keyword% queries generated by QueryDSL containsIgnoreCase() caused slow searches. Tests recorded response times of up to 60,735 ms.
  • The leading wildcard prevented B-tree range scans, resulting in full table scans.
  • Handling search, sorting, and pagination entirely in the database increased the cost as the data grew.

Solution

1. Introduce MySQL Full-Text Search

  • Added a FULLTEXT INDEX and N-gram parser to narrow candidate rows through an inverted index within the existing infrastructure.
  • Extended Hibernate FunctionContributor in a custom dialect to support MATCH … AGAINST and score-based sorting.
  • Reduced p95 latency to about 82 ms, but Filesort for created_at and rate ordering and scan costs for deep cursor pages remained.

2. Move search to Elasticsearch

  • Used the Nori morphological analyzer to reduce the overly broad matches produced by N-grams.
  • Implemented search_after cursor pagination with createdAt DESC and post_id DESC ordering.
  • Indexed only searchable fields. Elasticsearch returned post IDs, and MySQL findByIdIn loaded the entities. This reduced ES document-to-entity mapping while preserving JPA relationships.

Results

Approachp95 latency
LIKE60,735ms
MySQL FTS82ms
Elasticsearch78ms
  • Reduced response time: 60,735ms → 78ms, approximately 99.8% lower.
  • Separating the search model improved scalability and response times for large datasets.

Concurrency Control for Post Counters

Problem

  • When many requests targeted the same postId, SELECT → Modify(+1) → UPDATE could overwrite another request's increment, causing lost updates.
  • synchronized only coordinates threads within one JVM and could not protect counters across multiple servers.

Solution

Comparing six concurrency-control strategies

Tested k6 constant-arrival-rate workloads for 30 seconds at 10, 50, 100, 150, 200, and 300 RPS on a Ryzen 5 3600 with 16 GB RAM.

Compared correctness (actual database increments / requests), p95 latency, failure rate, CPU usage, and operational complexity.

StrategyComparison
No LockCorrectness dropped to 58.6% as load increased.
Pessimistic lockMaintained 100% correctness, but contention increased response times.
Optimistic lock + retriesHeavy contention on the same row caused conflicts and retries, reaching a 98.5% failure rate.
JPQL Atomic UpdateAchieved p95 latency of 71 ms and 100% correctness without additional infrastructure.
Redis distributed lockLock-acquisition timeouts and round-trip overhead increased failures at 300 RPS.
Redis write-behindReduced database load with p95 latency of 14 ms, but required loss-recovery measures and more operational work.

Selected approach: JPQL Atomic Update

At the tested scale, JPQL offered the best balance of latency, CPU usage, and operational cost. Redis write-behind remained the planned next step if database index updates became the bottleneck.

Results

Under a simulated load of 300 RPS, achieved p95 latency of 71 ms and 100% correctness.

Designing a Daily Post Reindexing Job

Problem

  • Changes to the user dictionary or synonym dictionary were not reflected in searches when the existing index was left unchanged.
  • Asynchronous listener failures, network issues, or Elasticsearch outages after a database commit could leave indexing incomplete.
  • A mismatch between the database and search index could hide existing posts or expose deleted ones in search results.

Solution

Reindex from the database as the source of truth

  • Create a new index, index the full dataset, and switch the alias. If the batch fails before cutover, searches continue using the existing index.
  • Record T0=(modified_at, id) at the start and a T1 watermark immediately after cutover, then reconcile changes within (T0, T1].
  • Use a Painless script to update a document only when DB.modified_at > ES.modified_at, preventing older data from overwriting newer documents.

Account for replica lag

  • Verify replication consistency using GTID before taking a snapshot from the replica.
  • Run catch-up reads against the primary to reduce the risk of missing changes due to replica lag.

Results

  • The daily batch restores index consistency against the database.
  • Dictionary updates are applied on every batch run.
  • The same pipeline can support other batch tasks, such as computing popular posts.

Optimizing Daily Post Reindexing

Problem

Reindexing roughly 2 million posts stalled under repeated large joins and single-worker processing. After more than 3 hours 20 minutes, the original batch was still stuck at around 600,000 posts.

  • The query first LEFT JOINed post with seven tables, joining and sorting 1.29 million rows.
  • LIMIT 2000 was applied last, processing far more than the required 2,000 rows. Each query took about 900 seconds.

Solution

1. Deferred join

  • Use a covering index to select and sort 2,000 post IDs first, applying LIMIT before the detail joins.
  • Join details only for the selected IDs, choosing the Place or Video join based on dtype.
  • Reduced query time from 900 seconds to 1.46 seconds and total batch time to 31 minutes.

2. Spring Batch Step Partitioning

Identified a bottleneck from repeated single-row index lookups accumulating random disk I/O.

Partitioned the modified_at range so each Worker Step could independently read → process → write.

Results

Query restructuring and parallel processing reindexed 2 million posts in 8 minutes 15 seconds.

Restructuring the Application Architecture

Problem

  • Meteor.js coupled frontend and backend logic, making it difficult to assess the impact of changes during maintenance.
  • Without referential integrity across relationships such as User–Factory–Worksite–Checklist, deleting parent records could leave orphaned data.

Solution

Separate application responsibilities

  • Separated backend responsibilities using an Express.js layered architecture.
  • Separated asynchronous logic and state management with React and Redux-Saga.

Migrate the database

  • Migrated from MongoDB to MySQL and modeled relationships with foreign keys.
  • Used ON DELETE CASCADE and indexes to strengthen consistency and query performance.

Results

  • Reduced the time needed to understand the code during maintenance.
  • Improved operational data consistency through ACID transactions and referential integrity.

Fixing Unexpected Logout

Problem

Automatic login could be lost after a server restart or WebView app termination if the session or cookie was not persisted.

  • MemoryStore sessions were lost when the server restarted or was redeployed.
  • Login information was lost when WebView cookies had not been written to disk before the Android app exited.

Solution

  • Moved session storage to MySQL using express-mysql-session so sessions could be recovered after a server restart.
  • Call CookieManager.flush() after a successful login to immediately persist in-memory cookies to device storage.

Results

Automatic login was preserved after server restarts and forced app termination.
